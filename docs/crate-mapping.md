# Rust crate mapping for Laravel capabilities

**Research snapshot:** 2026-11-18. This is a research shortlist, not a set of
selected dependencies or a claim of Laravel parity. Nothing here has been
installed in Kiln. Verify the exact release, feature flags, MSRV, license,
security posture, and compatibility with the chosen stack when implementing a
capability. Crate APIs and compatibility can change.

Kiln's v1 direction is to reuse existing libraries and write only the
integration needed to match the relevant Laravel 13 behavior. This mapping is
intentionally broad because the request is to identify potential wheels to
reuse; it does not mean every row belongs in v1 or needs a Kiln abstraction.

## Candidate map

| Laravel capability | Rust candidates | Fit and integration notes |
| --- | --- | --- |
| HTTP server, routes, handlers, extractors, responses | [`axum`](https://crates.io/crates/axum), [`tower`](https://crates.io/crates/tower), [`tower-http`](https://crates.io/crates/tower-http), [`hyper`](https://crates.io/crates/hyper) | Axum is a strong candidate for a composable handler/router layer; Tower supplies the service/layer model and tower-http has common HTTP middleware. Axum is intentionally tied to Tokio/Hyper/Tower, which makes this a coherent stack rather than a transport-neutral choice. Laravel-style route declarations, route names, controller conventions, and URL generation may still need integration. |
| Middleware, request IDs, timeouts, body limits, CORS, compression, static files | [`tower-http`](https://docs.rs/tower-http/latest/tower_http/) | Existing Tower layers cover these lower-level concerns (including CORS, trace, compression, limits, request IDs, and `ServeDir`). Compose only the layers required by Laravel's documented behavior; middleware ordering and safe CORS policy remain application configuration concerns. |
| WebSockets / realtime transport | Axum's [`ws` extractor](https://docs.rs/axum/latest/axum/extract/ws/), [`socketioxide`](https://crates.io/crates/socketioxide) | Axum includes WebSocket transport support behind a feature. Socketioxide implements the Socket.IO protocol, which is not the same thing as Laravel broadcasting or raw WebSockets; it is relevant only if protocol compatibility is desired. Event broadcasting, authorization, and channel semantics need separate mapping. |
| Database drivers and async SQL | [`sqlx`](https://crates.io/crates/sqlx) | Async SQL toolkit, connection pools, prepared statements, and optional compile-time checked query macros. Supports PostgreSQL, MySQL/MariaDB, and SQLite in current docs; it is explicitly not an ORM and does not supply Eloquent-style relations or model lifecycle conventions. |
| ORM / Active Record-style data access | [`sea-orm`](https://crates.io/crates/sea-orm), [`diesel`](https://crates.io/crates/diesel) | SeaORM is the closer high-level relational/ActiveRecord-like candidate, with entities, relations, eager loading, pagination, and migrations. Diesel offers a typed query DSL with compile-time schema checking and migration support, but has a different workflow and sync/async integration tradeoffs. Choose one based on verified v1 needs; do not stack ORMs. |
| SQL query construction | [`sea-query`](https://crates.io/crates/sea-query), SQLx [`QueryBuilder`](https://docs.rs/sqlx/latest/sqlx/struct.QueryBuilder.html), Diesel query DSL | Useful for dynamic filters and query construction. SeaQuery is also the query builder underlying SeaORM. Prefer the selected ORM/toolkit's query facilities unless a concrete integration gap justifies another dependency. |
| Schema migrations | [`sqlx-cli`](https://crates.io/crates/sqlx-cli), [`diesel_migrations`](https://crates.io/crates/diesel_migrations), [`sea-orm-migration`](https://crates.io/crates/sea-orm-migration), [`refinery`](https://crates.io/crates/refinery) | SQLx and Diesel have migration tooling; SeaORM has a matching migration crate/CLI; Refinery is a database migration toolkit for SQL files or Rust migrations. These formats and runtime behavior differ. Laravel migration-file compatibility is not established by these crates and must be assessed separately. |
| Factories, seeders, fake data, database test fixtures | [`fake`](https://crates.io/crates/fake), SQLx [`#[sqlx::test]`](https://docs.rs/sqlx/latest/sqlx/attr.test.html), SeaORM `MockDatabase` | `fake` creates representative values, not persisted Eloquent factories. SQLx tests can provision isolated databases and apply migration fixtures for supported setups; SeaORM offers a mock database for query behavior. Factory definitions, persistence, relationship creation, and Laravel seeder semantics need Kiln-side conventions or a verified specialized crate. |
| Validation / FormRequest-like validation | [`garde`](https://crates.io/crates/garde), [`validator`](https://crates.io/crates/validator), [`axum-valid`](https://crates.io/crates/axum-valid) | Garde and validator provide derive-based validation; axum-valid connects validators to Axum extractors. They do not by themselves reproduce Laravel's rule set, message localization, wildcard paths, authorization hooks, or JSON/redirect error behavior. Confirm each rule and response against Laravel 13 before exposing it. |
| Browser sessions and session persistence | [`tower-sessions`](https://crates.io/crates/tower-sessions), [`tower-sessions-sqlx-store`](https://crates.io/crates/tower-sessions-sqlx-store), [`tower-sessions-redis-store`](https://crates.io/crates/tower-sessions-redis-store) | Tower sessions provides middleware/extractor integration and a pluggable `SessionStore`; separate stores cover persistent backends. Select a store based on the chosen database/cache and verify cookie attributes, expiration, regeneration, flash data, and Laravel-compatible session behavior. PHP-serialized Laravel sessions are not directly interchangeable. |
| Authentication, guards, login state, authorization hooks | [`axum-login`](https://crates.io/crates/axum-login), `tower-sessions` | Axum-login supplies authenticated-user sessions, backend traits, and route protection, built on tower-sessions. It is a useful integration component, not a complete Laravel authentication starter: registration, password reset, email verification, confirmation, throttling, redirects, and starter screens must be matched to the Laravel 13 baseline. |
| OAuth / OpenID Connect | [`openidconnect`](https://crates.io/crates/openidconnect), [`oauth2`](https://crates.io/crates/oauth2), Axum integrations such as [`axum-open-id-connect`](https://crates.io/crates/axum-open-id-connect) | Protocol libraries can handle OIDC/OAuth flows; framework adapters may accelerate routing and session wiring. This is distinct from Laravel's built-in authentication starter and may be an optional integration, not default starter behavior. Verify security maintenance and protocol details before selection. |
| Password hashing | [`argon2`](https://crates.io/crates/argon2), [`password-auth`](https://crates.io/crates/password-auth) | RustCrypto's Argon2 implements Argon2id and the password-hash interface; password-auth offers a higher-level API and defaults to Argon2. Match Laravel's actual configured hashing behavior and migration/rehash strategy; perform expensive password work without blocking async request execution. |
| Authorization policies / roles / permissions | [`casbin`](https://crates.io/crates/casbin), `axum-login` | Casbin supports ACL, RBAC, and ABAC policy models, but explicitly does not provide user authentication or user/role management. Axum-login provides an authorization backend seam. Laravel gates/policies, policies discovery, and permission persistence are not drop-in equivalents. |
| CSRF protection | [`tower-http` CSRF module](https://docs.rs/tower-http/latest/tower_http/csrf/), [`axum-tower-sessions-csrf`](https://crates.io/crates/axum-tower-sessions-csrf) | These use different approaches: Tower HTTP's middleware checks `Sec-Fetch-Site` and `Origin` and requires no per-request token state; `axum-tower-sessions-csrf` implements a synchronizer-token pattern on tower-sessions. Check current release/API and security properties, plus Inertia/Axios cookie/header expectations. Choose based on the threat model and Laravel behavior to match; CSRF policy must align with session, cookie, and frontend setup. |
| Cookie parsing, signing, encryption | [`cookie`](https://crates.io/crates/cookie), Axum [`axum-extra`](https://crates.io/crates/axum-extra) cookie extractors | Cookie provides parsing and signed/private jars; axum-extra provides extractors. Signing is integrity, not confidentiality. Key generation, stable production key management, rotation, secure attributes, and Laravel cookie interoperability remain integration concerns. |
| Cache | [`moka`](https://crates.io/crates/moka), [`redis`](https://crates.io/crates/redis), [`fred`](https://crates.io/crates/fred) | Moka is an in-process concurrent cache; Redis clients support distributed cache storage. They are primitives, not a Laravel cache manager with its driver contract, serialization policy, tags, locks, and per-store configuration. Verify each Laravel feature against candidate APIs before claiming coverage. |
| Queue / background jobs / retries | [`apalis`](https://crates.io/crates/apalis) and backend crates; [`sqlxmq`](https://crates.io/crates/sqlxmq) | Apalis offers worker processing with Redis, PostgreSQL, SQLite, and other backends plus retry/middleware integrations. SQLxMQ is PostgreSQL-based and supports delayed work and retries. Compare delivery guarantees, failure handling, scheduling, backend support, and operational tooling with Laravel queues before choosing. |
| Scheduled tasks / cron | [`apalis-cron`](https://crates.io/crates/apalis-cron), [`cron`](https://crates.io/crates/cron), [`tokio-cron-scheduler`](https://crates.io/crates/tokio-cron-scheduler) | Apalis-cron integrates scheduling with its job workers and persistence options. A cron parser alone does not provide Laravel scheduler features such as overlap prevention, one-server execution, mutexes, or task output handling. Verify those semantics rather than assuming parity. |
| Events and in-process pub/sub | Tokio [`broadcast`](https://docs.rs/tokio/latest/tokio/sync/broadcast/), [`event-listener`](https://crates.io/crates/event-listener) | These provide process-local notification primitives, not a Laravel event dispatcher with discovery, queued listeners, wildcard events, or cross-process delivery. Use only for a concrete in-process event use case; queued delivery can build on the selected job system. |
| Notifications (email and future channels) | [`lettre`](https://crates.io/crates/lettre), selected queue crate | Lettre handles email messages/transports; the queue can deliver asynchronously. Neither is a multi-channel notification framework. SMS, database, broadcast, and per-user channel preferences require capability-specific crate research before implementation. |
| Mail composition and SMTP delivery | [`lettre`](https://crates.io/crates/lettre) | Message building and pluggable SMTP/sendmail/file transports, including async support. It does not provide a Laravel-style mailer configuration manager, notification channel dispatch, templates, or queue integration; those can be wired through the selected job system. |
| File uploads and local/object storage | Axum [`Multipart`](https://docs.rs/axum/latest/axum/extract/struct.Multipart.html), [`axum-typed-multipart`](https://crates.io/crates/axum-typed-multipart), [`object_store`](https://crates.io/crates/object_store), [`aws-sdk-s3`](https://crates.io/crates/aws-sdk-s3) | Axum multipart is built in behind a feature; typed multipart can derive typed extraction. `object_store` offers a common async object-store API for local and cloud stores. Upload limits, streaming, path safety, metadata, URL generation, visibility, and Storage facade semantics still need deliberate integration. |
| Static files and built frontend assets | [`tower-http` `ServeDir`](https://docs.rs/tower-http/latest/tower_http/services/fs/struct.ServeDir.html), [`rust-embed`](https://crates.io/crates/rust-embed) | ServeDir handles filesystem-backed static assets; rust-embed can embed assets in a binary. Neither selects/builds the frontend or reproduces Laravel Vite's manifest, dev-server, hot-file, and versioning conventions. |
| Inertia protocol / Vue and React integration | [`inertia-rust`](https://crates.io/crates/inertia-rust), [`inertia_rs` repository](https://github.com/stuarth/inertia-rs), [`axum-inertia`](https://crates.io/crates/axum-inertia), [`inertia-omega`](https://github.com/inertiajs/inertia-omega) | Candidates found include an Axum adapter (`axum-inertia`), an adapter project whose repository documents Axum/Rocket and Inertia v3 (`inertia_rs`), and a newer explicitly alpha protocol port (`inertia-omega`). The crates.io `inertia-rust` page documents a different major/protocol version. Verify the exact package/version, protocol version, completeness, license, and maintenance; search results and repositories show differing versions/status. Inertia's official Vue/React client packages and Vite remain JavaScript dependencies, not Rust crates. |
| Vite development/build manifest and asset tags | Official [Vite](https://vite.dev/), [`vite-rs`](https://crates.io/crates/vite-rs) (candidate) | Vite itself is the JS build tool. Rust helpers may read a manifest or generate tags, but no candidate has been verified here as a Laravel Vite-equivalent. A minimal integration may be smaller than adopting an unverified wrapper. |
| Configuration and environment | [`figment`](https://crates.io/crates/figment), [`config`](https://crates.io/crates/config), [`envy`](https://crates.io/crates/envy), [`dotenvy`](https://crates.io/crates/dotenvy) | Figment/config combine typed sources and overrides; envy deserializes environment variables into Serde types; dotenvy loads `.env` input. Pick based on the desired configuration-source and precedence model. dotenvy does not validate application settings. |
| JSON, form, query, serialization | [`serde`](https://crates.io/crates/serde), [`serde_json`](https://crates.io/crates/serde_json), Axum extractors | Serde is the ecosystem serialization foundation; Axum supplies JSON, form, path, and query extraction with rejection types. Laravel's request casting, response formatting, and validation error shape need explicit behavior mapping. |
| Outbound HTTP client | [`reqwest`](https://crates.io/crates/reqwest), [`hyper`](https://crates.io/crates/hyper) | Reqwest provides a high-level async HTTP client; Hyper is a lower-level HTTP implementation. These cover transport, not Laravel's configured HTTP-client facade, retry defaults, request macros, fakes, or response semantics. |
| Localization / translation messages | [`fluent-bundle`](https://crates.io/crates/fluent-bundle), [`rust-i18n`](https://crates.io/crates/rust-i18n) | Fluent provides message formatting; rust-i18n offers a macro-oriented translation workflow. Compare pluralization, locale negotiation, fallback, runtime catalogs, and validation/auth message integration with the required Laravel behavior. |
| Rate limiting | [`governor`](https://crates.io/crates/governor), [`tower-governor`](https://crates.io/crates/tower-governor), [`axum-governor`](https://crates.io/crates/axum-governor) | Governor provides rate-limiter primitives; Tower/Axum adapters provide middleware. Check whether limits are process-local or distributed and how keys, headers, storage, and Laravel throttle behavior should map. Trust proxy-derived client IPs only when proxy configuration is known. |
| Encryption and signed URLs | [`ring`](https://crates.io/crates/ring), [`RustCrypto`](https://github.com/RustCrypto) crates, [`cookie`](https://crates.io/crates/cookie) | Cryptographic primitives or cookie signing can support specific features; they are not a direct Laravel encrypter replacement. Laravel-compatible ciphertext formats, key rotation, authenticated encryption, URL signatures, and verification errors need their own precise mapping. Prefer a maintained high-level crate if one matches the required protocol rather than assembling primitives ad hoc. |
| API schema and generated documentation | [`utoipa`](https://crates.io/crates/utoipa), [`utoipa-axum`](https://crates.io/crates/utoipa-axum), [`utoipa-swagger-ui`](https://crates.io/crates/utoipa-swagger-ui) | Utoipa derives OpenAPI from Rust types/handlers; utoipa-axum can collect routes while generating a spec. Optional API documentation capability; it is not required for the Laravel application workflow itself. |
| Pagination | SeaORM's paginator/cursor APIs; [`paginator-rs`](https://crates.io/crates/paginator-rs) with `paginator-sqlx`, `paginator-sea-orm`, `paginator-axum` | SeaORM supplies offset and cursor pagination. The paginator family advertises page, offset, cursor, filtering, and SQLx/SeaORM/Axum integrations. Validate maturity and behavior, especially count queries, stable ordering, limits, and Laravel response shape, before adoption. |
| Logging, tracing, metrics, distributed tracing | [`tracing`](https://crates.io/crates/tracing), [`tracing-subscriber`](https://crates.io/crates/tracing-subscriber), [`tower-http`](https://crates.io/crates/tower-http), [`opentelemetry`](https://crates.io/crates/opentelemetry), [`tracing-opentelemetry`](https://crates.io/crates/tracing-opentelemetry) | Tracing and Tower HTTP provide structured diagnostics and request spans; OpenTelemetry crates export telemetry using OTLP. These are complementary pieces with version/feature alignment requirements, not a full Laravel Telescope replacement. |
| Error reporting | [`sentry`](https://crates.io/crates/sentry) | Optional hosted error/performance reporting SDK with tracing integration. It is service-specific and should remain optional; do not make it a core framework requirement. |
| CLI parsing, prompts, progress, scaffolding | [`clap`](https://crates.io/crates/clap), [`dialoguer`](https://crates.io/crates/dialoguer), [`indicatif`](https://crates.io/crates/indicatif), [`minijinja`](https://crates.io/crates/minijinja), [`include_dir`](https://crates.io/crates/include_dir), [`rust-embed`](https://crates.io/crates/rust-embed) | Clap handles commands/arguments; Dialoguer and Indicatif cover interactive prompts/progress; MiniJinja or filesystem embedding can support project templates. Cargo already provides package/workspace operations; template generation should avoid reimplementing Cargo behavior. |
| Application errors | [`thiserror`](https://crates.io/crates/thiserror), [`miette`](https://crates.io/crates/miette), [`anyhow`](https://crates.io/crates/anyhow) | `thiserror` helps define typed library errors; `miette` and `anyhow` can improve CLI diagnostics and error context. Keep typed framework/API errors at public boundaries; these crates do not decide Laravel-compatible HTTP error rendering. |

## Important candidates to investigate first

This is a shortlist for subsequent capability-specific verification, not a
dependency decision:

1. **Axum + Tower + tower-http** for an HTTP/Tower foundation, subject to the
   team's preference and Laravel routing/middleware behavior requirements.
2. **SQLx or SeaORM** for database access. They represent meaningfully different
   developer experiences; compare them against Laravel's query-builder and
   Eloquent workflows rather than choosing by feature count.
3. **Tower sessions + Axum login + Argon2** as building blocks for the required
   authentication starter. Confirm the complete Laravel 13 starter behavior;
   no single crate in this mapping has been verified to supply the whole
   starter.
4. **An Inertia server adapter** only after a compatibility spike against the
   Inertia protocol version and official Vue/React client packages. The
   candidates surfaced here have differing maturity and version claims.
5. **Apalis or SQLxMQ** for queued work, selected after matching Laravel queue
   backend and operational requirements.

## Gaps and cautions

- A crate feature is not automatically Laravel-equivalent. Preserve Laravel 13
  defaults, success/failure behavior, status codes, redirects, validation
  shape, and security behavior when translating a requested capability.
- Authentication starter kits are a composed experience, not just login
  middleware. The baseline remains the built-in authentication variant of the
  Laravel 13 official Vue/React starter kits documented in `CONTEXT.md`.
- Do not select both an ORM and a competing abstraction for the same job without
  a demonstrated integration requirement.
- Treat framework-specific adapters as compatibility constraints. Axum/Tower
  adapters are a natural fit only if Kiln adopts that stack; Actix, Rocket, and
  other runtimes may require different crates or adapters.
- Check crate licenses against the project's distribution plans. The list
  includes projects with differing licenses and should not be treated as
  pre-cleared.
- This list is intentionally not a promise to implement every Laravel feature.
  Research each requested capability against Laravel 13's documentation/source
  and the candidate's authoritative docs before adding dependencies.
